FlexClock — Full-Color LED Race Clock
Installation, updates and network management
===========================================

Repositories and configuration
------------------------------
/home/admin/sign-controller is LEDSign. Its web/ directory is the separate
LEDSign_Site repository. Publish compatible versions in both repositories.
Never reset working checkouts or include config/, passwords, runtime secrets,
virtual environments or customer-uploaded assets in Git. Existing settings.json
and logos are retained. Back up configuration privately before system changes.
Use the exact reviewed commit pair from the deployment report for reproduction.
The general installer still follows main; pin release revisions for distribution.

Website runtime
---------------
Flask/Waitress runs as the device user under sign-web, behind nginx on port 80.
Install only missing dependencies from web/requirements.txt; do not downgrade
already functioning packages merely to match older version pins. No frontend
build step is needed. The current environment passed tests with Flask 3.1.2,
Werkzeug 3.1.3, Pillow 11.3.0 and Waitress 3.0.2.
The installer updates checkouts by fast-forward only, preserves the installed
network manager, and does not start the LED controller. Do not use the complete
installer for a small update to an existing device.
The previously installed sign-ui unit incorrectly launches a duplicate website.
It was stopped with approval. Do not start it or enable a second web process on
port 8000; controller startup repair is separate from website deployment.

Wi-Fi setup for the installed network stack
------------------------------------------
This installation uses dhcpcd with wpa_supplicant. NetworkManager is installed but
inactive. The generic wpa_supplicant D-Bus service does not by itself attach wlan0.
The missing wlan0 control socket was caused by having neither an interface unit
nor a dhcpcd wpa_supplicant startup hook and no Wi-Fi configuration file.

For this stack, the reproducible interface setup is:
  sudo bash /home/admin/sign-controller/scripts/setup_wifi.sh
The script creates/preserves /etc/wpa_supplicant/wpa_supplicant-wlan0.conf, enables
saving via update_config=1, configures its control socket, preserves saved network
blocks, and uses the regulatory country already selected in the OS. Set the
correct country during OS provisioning; no frequency restriction is imposed by
the website. The script enables/starts only wpa_supplicant@wlan0.service. If
another working supplicant already controls wlan0, it leaves that setup alone.
It refuses a conflicting active NetworkManager stack and never switches managers
or resets Ethernet. It first runs the DHCP client upgrade below when necessary. The installer invokes this setup
for fresh deployments using the supported stack.

Install helpers and narrow permissions
-------------------------------------
sudo install -d -m 0755 /usr/local/libexec/flexclock
sudo install -o root -g root -m 0755 scripts/web_network.py /usr/local/libexec/flexclock/web_network.py
sudo install -o root -g root -m 0755 scripts/web_hostname.py /usr/local/libexec/flexclock/web_hostname.py

Use visudo to install this rule for the actual device user (admin here):
admin ALL=(root) NOPASSWD: /usr/local/libexec/flexclock/web_network.py scan, /usr/local/libexec/flexclock/web_network.py wifi, /usr/local/libexec/flexclock/web_network.py wifi_address, /usr/local/libexec/flexclock/web_network.py ethernet, /usr/local/libexec/flexclock/web_hostname.py ""

Validate with sudo visudo -c before deploying. Helpers must remain root-owned;
never grant sudo to user-writable scripts or arbitrary network commands.
The old /etc/flexclock-network-enabled file is no longer used. There is no
commissioning-file gate. Authentication, CSRF, explicit application confirmation,
root-side validation, interface allowlists and active-stack checks remain.
Mutating helper calls are serialized with a root-owned /run lock to avoid
simultaneous connection/configuration changes. Scans remain read-only queries.

Using Wi-Fi
-----------
Scan Networks lists each named network once with its strongest observed signal.
Select it or enter a hidden network name, choose security, enter the password and
Connect. WPA/WPA2 Personal and open networks are supported. Enterprise/WPA3-only
networks require additional OS configuration. Passwords are received on stdin,
converted to a derived PSK, never echoed or logged, and saved in the OS Wi-Fi file
with mode 0600. The Wi-Fi interface unit uses UMask=0077, and the helper
reasserts 0600 after saving so wpa_supplicant cannot leave credentials world-readable. Do not publish that file or even the derived PSK.
The helper listens for authentication errors, verifies association with the
requested network, saves the profile only after association, and separately waits
for an IP address. No IP is reported as a warning, not a fully working connection.
Failed attempts remove the temporary profile and reload previously saved Wi-Fi
settings. Replacing a saved network removes duplicate profiles only on success.
Disconnect disables saved profiles and saves that choice before disconnecting;
connecting again enables the selected profile. No Ethernet change is involved.

Wi-Fi DHCP and static addressing
-------------------------------
The separate Wi-Fi Address form offers Automatic (DHCP) or Fixed address (Static).
Static requires IP, dotted subnet mask, gateway and DNS. The helper validates
again, rejects an address used by the other connection, backs up dhcpcd.conf and
replaces only the tagged wlan0 block. It runs only dhcpcd -n wlan0. A metric of
3000 keeps the existing Ethernet metric (1002 on this device) preferred.
DHCP verification requires a dynamic address; static verification requires the
requested address and mask without the old DHCP flag. Thus a stale address does
not count as proof the new setting applied. Saved settings and application are
reported separately if no matching address appears.
These Wi-Fi address settings apply to wlan0 across saved Wi-Fi networks. They are
not separate address profiles per SSID. Choose DHCP before moving to a different
network if a fixed address is not appropriate for it.
Ethernet uses its separate tagged block and dhcpcd -n eth0 only after confirmation.
The backup is /etc/dhcpcd.conf.flexclock-backup; each address change replaces it.
Private deployment backups retain the original state. Normal address changes never restart the shared daemon. The one-time
client upgrade below replaces its running process while preserving addresses. Do not apply Ethernet changes merely to test the website.

Website behavior and access
---------------------------
Ethernet and Wi-Fi each have visible connection details and settings. Gateways,
DNS and subnet masks come from per-interface OS observations, not raw output.
No expandable sections, Linux commands or developer diagnostics belong on normal
configuration pages. Confirmation uses the shared application modal, never a
browser confirm dialog. Static CSS/JS URLs carry content hashes to bypass cache.

Admin passwords require 5–128 characters with no character-class rules. Current
password and matching confirmation are required; hashes are saved atomically and
all sessions are invalidated after a change. config/.web-secret (0600) must survive
worker/service restarts and stay outside Git. SC_SECRET can override it. Use TLS
and SESSION_COOKIE_SECURE on untrusted networks.
Mixed-case device names normalize to lowercase (FlexClock1 -> flexclock1) before
both Flask and the root helper validate. Hostname changes use hostnamectl and are
verified after saving. Name-discovery and OS /etc/hosts aliases may need separate
OS provisioning; no network-manager restart is needed for a hostname change.

Logging
-------
The authenticated Logging page shows searchable, plain-language activity for five
allowlisted services, including the actual wpa_supplicant@wlan0 Wi-Fi service.
Queries cover up to 1,000 entries in the selected hour/day/week and paginate 50
results. Search applies to displayed messages and service names. Raw traces,
passwords and commands are not exposed. Unknown diagnostics are summarized.
The current admin user can read journals via adm; fresh installations give only
sign-web SupplementaryGroups=systemd-journal. No sudo journal command is needed.

Testing and deployment
----------------------

venv/bin/python -m py_compile web/app.py web/device.py web/activity.py scripts/web_network.py scripts/web_hostname.py

Automated tests mock disruptive operations and use temporary credentials/settings.
For the live Riley test, the user explicitly authorized Wi-Fi configuration and
connection changes while keeping Ethernet connected. No real admin password or
hostname change is required. Never store the supplied Wi-Fi password in a test
fixture, source file, report or repository.

Deploy reviewed website code/helper/sudoers and restart only sign-web. A Wi-Fi
service restart for persistence testing is separate and must be authorized.
Verify association, assigned IP, DNS, gateway reachability bound to wlan0, Ethernet
address/route preservation, and reconnect from the saved profile. Enabling the
interface service and saving settings prepare reboot persistence; they do not
prove it. Do not claim a reboot test unless an actual reboot was performed.
Browser rendering remains a separate desktop/tablet/mobile check if no browser
is available. Physical LED control and FinishLynx integration remain separate.


Required DHCP client fix on Debian 12
------------------------------------
The original dhcpcd 9.4.1 control interface returned success without applying some
interface updates (journal: cannot handle another client). Do not count a rebind
exit code as proof. The signed Debian Bookworm backport 1:10.1.0-11~bpo12+3 was
installed for dhcpcd-base, dhcpcd and dhcpcd5; no other packages were upgraded.
Package information: https://packages.debian.org/bookworm-backports/dhcpcd-base

Reproduce the one-time repair with:
  sudo bash scripts/upgrade_network.sh
setup_wifi.sh calls it automatically. Version 10.1 or newer is left unchanged.
The script adds the official signed Bookworm backports source, keeps existing
config files and requires persistent address handling before handoff. It replaces
the old daemon using SIGTERM (its old control socket is broken) then starts the
new daemon. Existing kernel addresses/routes stay installed. During the actual
upgrade, Ethernet monitoring received 150/150 gateway replies, with no packet
loss; the Ethernet IP and routes remained unchanged. Subsequent DHCP/static
updates use only the selected interface and the fixed control interface.
The tested package version is pinned in the script; DHCPCD_VERSION is an explicit
installer override if a reviewed newer backport is selected. Never run a general
system upgrade as part of this repair. No reboot is needed.
